# 整体设计架构

本文档描述 AI Fiction Studio 的业务设计架构。它不是代码架构，也不是前后端技术分层，而是说明系统如何围绕“长篇小说创作”组织提示词、记忆、写作风格、任务链路、质量审计和修复闭环。

## 设计目标

AI Fiction Studio 不是一个简单的“输入大纲，生成正文”的工具。它的核心目标是构建一套长篇小说生产系统：

- 把零散脑洞变成稳定项目方案。
- 把项目方案沉淀为长期记忆。
- 把世界观、角色、势力、卷轴、章节蓝图拆成可控资产。
- 让 Prompt 按阶段分工，而不是用一个万能提示词硬写到底。
- 让 AI 写作时能读取当前阶段需要的记忆，而不是盲目塞全文。
- 让质量审计能反过来驱动局部修复、整章优化和记忆更新。
- 让写作风格 Skill 成为跨项目共享能力，而不是某本书的私有字段。

## 核心设计原则

### 1. 先策划，后生成

系统不会直接从一句灵感跳到正文。它先把故事拆成可长期维护的创作资产：

```text
灵感
  -> 项目策划对话
  -> 项目草案
  -> 边界锁定
  -> 长篇阶段规划
  -> 世界观 / 角色 / 势力
  -> 全书大纲
  -> 卷轴弧线
  -> 章节蓝图
  -> 正文
```

这样做的原因是长篇小说的核心问题不是“单章能不能写出来”，而是：

- 前 20 万字能不能抓人。
- 主线能不能持续推进。
- 角色和势力能不能撑住篇幅。
- 伏笔能不能回收。
- 世界规则会不会写崩。
- 章节之间有没有承接。

### 2. 创作资产分层

不同资产承担不同职责，不能混在一起。

| 层级 | 资产 | 职责 |
|---|---|---|
| 项目层 | 书名、简介、核心主题、策划记忆 | 决定这本书写什么、为什么能追读 |
| 世界层 | 世界观、硬约束、文风氛围、生成限制 | 决定世界怎么运行、什么不能违反 |
| 人物层 | 角色、势力、关系、语言指纹 | 决定谁在推动故事、他们如何说话和变化 |
| 结构层 | 全书大纲、卷轴、弧线、章节蓝图 | 决定长期节奏、阶段目标、章节功能 |
| 正文层 | 章节正文、钩子、摘要、状态快照 | 决定读者实际看到的内容 |
| 质量层 | 审计分数、问题清单、修复记录 | 决定文本是否可读、是否需要优化 |

### 3. Prompt 按任务分工

系统提示词不是一个大模板，而是一组按创作阶段分工的 Prompt。

```text
项目策划 Prompt
  负责把脑洞变成项目方案

世界观 Prompt
  负责规则、社会结构、力量体系、硬约束

角色势力 Prompt
  负责人物动机、行为模式、语言指纹、组织利益

大纲 Prompt
  负责全书结构、分卷、长期驱动力

弧线 Prompt
  负责每卷内部阶段目标、误判、反转、余波

章节蓝图 Prompt
  负责单章功能、承接关系、关键事件和钩子

正文写作 Prompt
  负责可读性、对白、场景、动作、情绪和追读

审计 Prompt
  负责找问题、定位原文、给严重度和修复建议

修复 Prompt
  负责只改该改的范围，不越权改剧情

状态提取 Prompt
  负责把写完的章节沉淀成可长期使用的记忆
```

这种设计避免几个常见问题：

- 大纲 Prompt 写正文。
- 审计 Prompt 擅自重写。
- 修复 Prompt 覆盖整章。
- 写作 Prompt 忘记世界硬约束。
- 项目策划每轮对话都跑偏。

### 4. 记忆不是聊天记录

系统不把所有历史聊天原样塞进 Prompt。聊天记录只是一种来源，真正进入长期上下文的是结构化记忆。

```text
聊天记录
  -> 项目策划记忆
  -> 核心引擎
  -> 读者承诺
  -> 边界锁定
  -> 长篇阶段规划
```

正文也不是全量塞入 Prompt，而是沉淀为：

- 章节摘要。
- 上承状态。
- 下接状态。
- 章末钩子。
- 关键事件。
- 角色状态变化。
- 伏笔投放和回收。
- 时间线事件。

这样做的原因是长篇小说动辄百万字，全文塞入 Prompt 不现实，也会污染上下文。系统需要的是“当前任务所需的事实”，不是所有文本。

## Prompt 设计架构

### Prompt 分层

```text
System Role
  决定 AI 身份：结构顾问 / 世界设计师 / 类型小说家 / 编辑

Task Prompt
  决定当前任务：策划 / 大纲 / 写作 / 审计 / 修复

Project Context
  当前项目事实：简介、主题、世界观、角色、势力、大纲

Memory Context
  长期记忆：策划记忆、角色状态、伏笔、时间线、章节状态

Writing Controls
  写作设置：通俗度、节奏、对白密度、描写密度、幽默、信息密度

Style Skill
  共享写作方法：人物、情绪、场景、冲突、语言、章节结构

Output Schema
  强制输出 JSON 或指定格式

Safety Boundary
  禁止越权、禁止改已写事实、禁止复制样本、禁止胡乱合并章节
```

### Prompt 优先级

当规则冲突时，优先级应该是：

```text
已写正文事实
  > 世界硬约束
  > 项目边界锁定
  > 当前章节蓝图
  > 角色当前状态
  > 卷轴/弧线规划
  > 写作设置
  > 写作风格 Skill
  > 通用写作偏好
```

写作风格 Skill 只能影响“怎么写”，不能覆盖“写什么”。例如 Skill 可以影响对白密度、情绪铺垫、场景组织，但不能把项目改成样本的剧情、人名、组织或世界观。

### 事实与建议分离

长篇写作里最危险的问题之一是记忆污染。系统必须区分：

| 类型 | 是否可当事实 | 示例 |
|---|---|---|
| 已写正文 | 是 | 第 12 章主角已经拿到证据 |
| 已落库设定 | 是 | 世界硬约束、角色当前状态 |
| 大纲规划 | 有条件 | 后续可能发生，但未写成正文前不能当既成事实 |
| 审计建议 | 否 | “建议补照相机来历”不是剧情事实 |
| 用户吐槽 | 否 | “这里不好看”不是设定 |
| AI 调整草案 | 否 | 未确认落库前只是建议 |

## 写作风格 Skill 设计架构

写作风格 Skill 是共享资产，不属于某一个项目。

```text
小说样本文件
  -> 上传
  -> 创建后台任务
  -> 后端多点代表性采样
       ├── 开篇章节
       ├── 前期章节
       ├── 中段章节
       ├── 后期章节
       └── 结尾附近章节
  -> 抽取写法工艺
       ├── 技法谱系
       ├── 前20万字留存模型
       ├── 人物
       ├── 情绪
       ├── 世界
       ├── 场景
       ├── 冲突
       ├── 关系
       ├── 细节
       ├── 信息差
       ├── 读者反馈
       ├── 语言
       ├── 角色声音矩阵
       ├── 场景施工模板
       ├── 篇幅适配
       ├── 文笔工艺
       ├── 段落推进
       ├── 场景真实感
       ├── 章节生产法
       ├── 偏离检测
       └── 修复策略
  -> 生成共享 Skill
  -> 项目选择引用
  -> 注入创建 / 世界观 / 角色 / 大纲 / 弧线 / 蓝图 / 正文 / 审计 / 修复
```

Skill 的边界：

- 不保存样本全文。
- 不复制原文句子。
- 不复刻样本剧情桥段。
- 不沿用样本人名、地名、组织名、专有设定。
- 只抽取抽象写作手法。
- 多个项目可以引用同一个 Skill。

Skill 抽取任务必须异步执行。大文件上传后，前端只显示文件名和任务状态，不把全文渲染到页面，也不让 HTTP 请求等待 AI 分析完成。任务完成后，生成的 Skill 自动进入共享库。

深度 Skill 不只记录“快节奏、强爽点、人物鲜明”这类标签，还要拆出作者实际写法：

- 章节如何切入。
- 人物如何通过动作、称呼、对白和反应出场。
- 细节如何承担人物、情绪、伏笔和现实阻力。
- 句子和段落如何形成节奏。
- 设定如何通过争论、行动、误解和利益冲突释放。
- 情绪如何落在物件、沉默、身体反应和未说出口的话上。
- 章节如何从开场、铺垫、冲突、解释、情绪落点走到结尾钩子。
- 前 20 万字如何立主角、给核心卖点、制造阶段反馈、扩地图和维持追读。
- 长篇、超长篇如何控制阶段目标、循环结构、敌人梯度、设定扩容和疲劳感。
- 写偏之后如何按原句、段落、整章轻修和整章重写拉回风格。

## 写作工作流设计

### 单章写作链路

```text
选择章节
  -> 获取项目事实
  -> 获取世界硬约束
  -> 获取角色/势力状态
  -> 获取当前卷和弧线目标
  -> 获取章节蓝图
  -> 获取最近章节承接
  -> 获取写作设置
  -> 获取当前项目引用的 Skill
  -> 生成正文
  -> 自动质量审计
  -> 可选轻修
  -> 写入章节
  -> 提取状态
  -> 更新记忆
```

### 批量写作链路

```text
选择弧线
  -> 找到未写章节
  -> 逐章构造上下文
  -> 承接上一章结尾和钩子
  -> 写一章
  -> 审计/轻修
  -> 更新当前批次上下文
  -> 写下一章
```

批量写作不能简单并发，因为后一章需要前一章的结尾、钩子和状态快照。

## 质量闭环设计

质量系统不是单纯打分，而是为了驱动可执行修复。

```text
章节正文
  -> 质量审计
       ├── 总分
       ├── 维度分
       ├── 主要问题
       ├── 问题定位
       ├── 严重度
       ├── 推荐修复范围
       └── 修复建议
  -> 修复入口
       ├── 只修原句
       ├── 修这一段
       ├── 深修局部上下文
       ├── 整章轻修
       └── 整章重写
  -> 保存版本
  -> 更新质量状态
```

质量闭环的核心原则：

- 审计只指出问题，不直接改正文。
- 局部修复必须精确定位，不允许整章漂移。
- 整章重写必须保存版本。
- 修复完成后要有状态变化，不让问题一直挂着。
- 审计建议不能自动变成剧情事实。

## 大纲调整设计

大纲和卷轴调整采用“先对话，后落库”的设计。

```text
用户表达不满
  -> AI 先整理理解
  -> 形成最终调整要求
  -> 用户确认范围
       ├── 只改卷故事大概
       └── 改本卷后续大纲/弧线/章节蓝图
  -> 后端按范围应用
  -> 清理旧的章节蓝图/景观/质量关联数据
```

设计重点：

- 不把一句吐槽直接写进数据库。
- 不因为“同一场景跨章节”就建议合并章节。
- 已写正文不能被大纲调整覆盖。
- 重拆弧线时必须清理旧章节、关键事件景观线、质量面板关联数据。

## 前 20 万字吸引力设计

长篇网文的前 20 万字需要特别处理，系统在策划、大纲、弧线、章节写作中都要关注：

- 开篇主角目标是否清楚。
- 冲突是否具体。
- 读者承诺是否足够早出现。
- 爽点、笑点、悬念、危机是否有稳定循环。
- 反派压力是否持续升级。
- 每章是否有继续读下一章的动机。
- 设定是否通过事件释放，而不是说明书。
- 人物关系是否有早期抓手。

这不是单个 Prompt 能解决的问题，而是贯穿整个工作流的设计目标。

## 未来设计方向

### Prompt Registry

把当前代码内 Prompt 演进为可视化注册表：

- Prompt key。
- 版本。
- 系统角色。
- 输出 schema。
- 适用任务。
- 项目级覆盖。
- 测试样例。
- 版本 diff。

### Memory Registry

把记忆来源和用途显式管理：

- 哪些记忆进入写作。
- 哪些记忆只用于展示。
- 哪些是事实。
- 哪些是草案。
- 哪些来自审计。
- 哪些需要用户确认。

### Skill Marketplace

共享 Skill 可以进一步演进为：

- 私有 Skill。
- 公共 Skill。
- 项目默认 Skill。
- 按任务启用的 Skill。
- 多 Skill 混合。
- Skill 效果评分。

### 更强质量闭环

质量系统后续可以继续增强：

- 修复前后分数对比。
- 问题状态流转。
- 章节质量趋势。
- 前 20 万字吸引力专项面板。
- 弧线级质量审计。
- 风格一致性审计。

## 一句话总结

AI Fiction Studio 的整体设计不是“让 AI 一次性写完小说”，而是把小说创作拆成可管理的资产、记忆、Prompt、任务和质量闭环，让 AI 在每个阶段做明确的事，并把结果沉淀回长期创作系统。
