# 更新说明

本文记录近期对长篇连续性、数据库迁移和开源升级流程的关键更新。升级旧项目或二次开发前建议先阅读本页。

文档维护规则：每次更新都追加独立条目；即使是同一天的多次更新，也使用时间或主题区分，不覆盖、不改写已有更新说明。

## 2026-06-13 展开弧线章节 - AI 任务详情预览

本次更新优化“展开弧线章节”的任务结果查看体验，并调整模型调用参数。

### 调整内容

- `expand_arc_chapters` 调用不再传 `max_tokens` 字段，交由模型供应商按当前模型能力处理输出上限。
- AI 任务详情中，`展开弧线章节` 的结果不再只展示大段 JSON，而是增加可读的章节蓝图预览。
- 预览按章节卡片展示章节序号、标题、章节功能、张力、摘要、上承、下启、弧线台阶、关键事件、小事件/伏笔、下章承接和场景序列。
- 原始 JSON 仍保留在折叠区域，方便排查字段、复制原始返回或对照模型输出。
- 后端不对整章蓝图字段做预算裁剪，不截断模型返回字段，完整保留 AI 输出结构。

### 追加优化：降低 token 和耗时

针对 `展开弧线章节` 日志中输入 token 高、输出过长、耗时较久的问题，进一步优化提示词：

- 为 `expand_arc_chapters` 使用专用短 system prompt，不再每次附带完整总策划系统提示。
- 精简章节展开提示词，删除重复的角色预算、关系预算、对手预算、场景簇预算和多轮自检长段说明。
- 保留章节档位、连续性、前后交接、章节增量、字段 schema 和输出长度约束，避免为了省 token 牺牲可用性。
- 输出仍然是完整章节蓝图 JSON 数组；后端不裁剪、不截断、不二次删字段。
- `max_tokens` 仍不传，由供应商按模型能力处理。

### 追加修复：承接上一弧线最后章节钩子

修复 `展开弧线章节` 只承接上一弧线结构状态，但可能没有明确接住上一弧线最后一章追读钩子的问题。

- 展开非第一条弧线章节时，后端会明确读取上一弧线最后一章。
- 独立提取上一弧线最后一章的正文 `[HOOK]`、`connects_to`、`hook_design` 和 `continuity_to_next`。
- 将该信息作为 `previous_arc_last_hook` 传给章节蓝图模型，不再只混入上一弧线结尾状态。
- 提示词要求当前弧线第 1 章必须在 `summary`、`connects_from`、`continuity_from_previous` 或 `opening_requirements` 中明确回应上一弧线最后章节钩子。
- 生成首章蓝图时会保存 `previous_arc_last_hook`，方便后续写正文、诊断和排查连续性问题。

### 追加调整：章节数量和张力不再过度保守

修复压缩提示词后 `展开弧线章节` 可能章节偏少、张力偏低的问题。

- 章节数规则改为优先遵守后端计算出的“章数提示”，通用档位只做兜底。
- 除桥接/余波弧线外，标准展开默认取建议区间中位，长展开/细写取中高位，避免模型主动压到下限。
- 增加张力规则：普通推进章通常为 5-7，关键冲突/反转/钩子章应为 8-10。
- 要求每 2-3 章至少出现一次压力升级、误判、反制、期限、利益损失、关系裂痕或新证据。
- 修正 JSON 示例中的低张力暗示，将 `hook_strength` 示例从 1 调整为 4，将 `tension_level` 示例从 1 调整为 6。
- 前端展开章节默认值改为 `长展开 + 事件丰富 + 适中节奏`，更符合长篇连载默认需求；仍可手动切回短展开或标准展开。

### 升级说明

本次更新没有数据库结构变更，不需要执行升级 SQL。

## 2026-06-13 质量大盘 - 按章节聚合修复问题组

本次更新优化质量大盘的问题修复入口，解决“同一章多个连续性问题被拆成多条，用户只能一条一条点修复”的问题。

### 追加调整：写作流程默认改为稳定草稿

本次调整解决“写一个弧线章节太费劲：批量写完后自动审计、自动轻修、复审、再修复，越修问题越多”的流程问题。

问题原因：

- 弧线批量写作后，系统可能为每章自动触发审计任务。
- 如果开启自动轻修，写完一章会立刻进入“审计 -> 轻修 -> 二次审计”链路。
- 局部轻修容易只盯当前问题，破坏上一章钩子、章节容量、人物已知信息和章末状态。
- 对长篇连载来说，成稿阶段应该先保证弧线连续写完，再做统一质量处理，而不是边写边局部修。

调整内容：

- 写作总控默认改为 `stable_draft` 稳定草稿模式。
- 前端默认关闭 `auto_quality_check`、`auto_light_fix` 和 `async_quality_check`。
- 弧线批量写作强制使用稳定草稿模式：只负责把弧线章节连续写完，不再自动挂后台审计任务，也不自动轻修正文。
- 旧项目如果保存过早期的自动轻修配置，但没有新版 `write_flow_mode`，后端会自动按稳定草稿处理，避免旧配置继续触发危险链路。
- 写作设置中的“质量链路”改为：
  - 稳定草稿（推荐）
  - 写后只审稿
  - 审稿并轻修（谨慎）
- 推荐工作流改为：先拆章节并批量成稿，再进入质量大盘按章节问题组统一处理，不再逐条来回修。

本次追加调整没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：章节审计基准使用上一章状态

本次修复“章节连续修复多轮后仍不断报同类问题”的审计基准错误。

问题原因：

- 单章审计时，系统把“当前章自己的 `story_state_snapshot`”传给审计模型，作为“故事当前状态快照”。
- 这会导致审计模型拿当前章已经发生的结尾信息去审当前章正文。
- 典型表现是：第 9 章结尾出现李长河后，复审会误判“上一章已经出现李长河，本章重复发现”；或者当前章状态里已有审干科来信，复审又误判正文重复递交文件。
- 用户反复修正文也无法解决，因为错误来自审计输入，而不是正文。

调整内容：

- `_do_audit_chapter` 改为使用上一章正文、上一章 hook 和上一章状态快照作为审计基准。
- 修复后复审也改为使用上一章状态快照，不再传入当前章自己的快照。
- 按评审修复后的 `reaudit` 分支同步修正。
- 自动审稿分支的 `previous_hook` 改为上一章 hook，避免拿当前章 hook 审当前章。
- 对第 9 章《上报后备干部》执行数据恢复：当前坏稿已保存为 v6 `manual_recovery` 备份，正文恢复到 v2，清空旧质量问题和错误状态快照。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

### 问题原因

章节审稿会把开场断裂、上一章钩子未回应、人物已知信息倒退、章末状态与快照冲突等问题拆成多条。它们在展示上是多条问题，但业务上往往属于同一章的同一组连续性断裂。如果逐条修复，模型容易只修当前问题，忽略同章其他问题，甚至产生新的局部冲突。

### 调整内容

- 质量大盘新增“按章节处理”标签页。
- 同一章的所有质量问题会聚合成一个章节问题组，显示最高严重度、问题数量、定位和建议。
- 新增“修复本章全部问题”按钮，一次性把该章全部问题作为整章修复清单提交给修订任务。
- 章节明细中如果某章存在多条问题，也会优先显示“修复本章全部问题”。
- 原有单条修复入口保留，适合定位明确的小问题；连续性断裂、钩子未承接、状态倒退等问题建议使用章节级修复。

本次更新只改前端聚合与修复上下文，没有数据库结构变更，不需要执行升级 SQL。

### 追加调整：章节明细内查看问题清单

为避免“章节明细”“问题清单”“按章节处理”三个入口互相重复，质量大盘进一步收敛为以章节明细为主入口：

- 移除独立的“按章节处理”列表。
- 移除底部单独的章节问题清单表。
- 章节明细中直接显示本章问题数量、首个问题和定位摘要。
- 新增“查看问题”弹框，展示某一章完整问题清单、定位和修复建议。
- 弹框内提供“修复本章全部问题”和“重新审稿”操作。
- 原有问题队列保留为全局总控入口，用于跨层级查看项目、世界观、大纲、卷轴、弧线、章节和任务问题。

本次追加调整只改前端交互，没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：整组修复防缩水

本次修复“修复本章全部问题”时模型输出明显短于原文，触发后端写回保护导致任务失败的问题。

调整内容：

- 新增 `quality_group_fix` 修订模式，专门用于同章问题组的整章连续性修复。
- `quality_group_fix` 纳入后端写回保护，仍要求修复后至少保留原文约 90% 字数。
- 前端提交整组修复前会读取原章节正文长度，并在提示词中明确写入原文字数和最低输出字数。
- 后端修复上下文增加 `min_output_chars` 和最低字数规则，让模型知道低于阈值会被拒绝写入。
- 修订提示词明确要求：整组修复不是摘要压缩，必须通过补足过渡、物件承接、人物反应和必要场景实写来解决连续性问题。
- 如果模型仍输出缩水正文，后端仍会拒绝写入，避免覆盖原稿。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：禁止修复稿重演上一章正文

本次修复“修复本章全部问题”后质量反而下降的问题：模型在处理“上一章钩子未承接”时，把上一章已经发生的张明远办公室场景重新写进本章，造成时间线倒流、情节重复和人物信息倒退。

调整内容：

- 修订提示词明确规定：上一章内容只能作为承接上下文，不能复制上一章已发生的完整场景、对话和动作。
- `quality_group_fix` 遇到“上一章钩子未承接”时，只能写本章当前时间点的后果、物件在身、人物反应、短回忆或过渡，不能重演上一章递文件、说原话、揭示信息的场景。
- 后端写回保护新增上一章正文重叠检测：如果修复稿包含上一章长段落或重复上章已完成场景，会拒绝写入，避免越修越坏。
- 修复上下文新增反复制规则，告诉模型“上章是上下文，不是本章正文素材”。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：工作台章节版本入口可用

本次修复工作台章节工具栏“版本”按钮点击无反应的问题。

问题原因：

- 后端已有章节版本接口，前端 API 也已封装 `versions`、`snapshot`、`restoreVersion`。
- 工作台工具栏里的“版本”按钮只是静态按钮，没有绑定弹窗、列表加载和恢复操作。

调整内容：

- “版本”按钮现在会打开章节版本弹窗。
- 弹窗支持查看版本号、来源、备注、字数和创建时间。
- 版本列表新增“查看”按钮，可在恢复前预览完整版本正文、字数、来源、备注和时间。
- 版本预览弹窗内也提供“恢复这个版本”，避免用户盲选恢复。
- 支持手动保存当前章节快照。
- 支持从历史版本恢复章节正文；恢复前后端会自动保存当前正文为“恢复前备份”，避免二次误操作。
- 版本加载和恢复失败会在前端给出错误提示，不再表现为“点了没反应”。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：复审不再为凑数量制造问题

本次修复“章节修复后每次复审仍固定出现 5 个问题，只是问题内容不断变化”的体验问题。

问题原因：

- 章节审计提示词列出了 20 个检查维度，并写了 `issues 最多 5 条`，模型容易误解为“需要挑 5 条问题输出”。
- 修复后的复审没有明确要求判断“原问题是否已解决”，模型会把普通润色建议继续塞进 `issues`，导致用户感觉永远修不完。

调整内容：

- 审计提示词明确允许 `issues=[]`。
- 明确禁止为了显得严格而凑满 5 条问题。
- `issues` 只放必须修复的问题：会导致读者卡住、剧情断裂、人物逻辑崩坏或后续状态错误。
- 普通润色、轻微文风、可选细节补强改放 `suggestions`，不进入问题清单。
- 修复后的复审必须判断当前问题是否已经解决，不得换一批低风险建议继续判失败。
- 后端保存审计结果时增加归一化：如果总分 `>=8` 且没有 `critical/high` 问题，会把 `low` 问题转入 `suggestions`，并将当前问题清单清空。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

### 追加修复：严重问题与质量分一致

本次修复“章节质量显示 9/10，但问题清单里仍有严重问题”的矛盾展示。

调整内容：

- 后端保存审计结果时增加分数封顶：
  - 存在 `critical` / `致命` 问题时，综合分最高显示为 6 分。
  - 存在 `high` / `严重` 问题时，综合分最高显示为 7 分。
- 质量大盘读取旧审计数据时也会按同一规则重新计算展示分，避免旧数据继续显示“高分 + 严重问题”。
- 轻微问题不会触发封顶；如果章节 9 分只剩轻微建议，应进入 `suggestions` 而不是当前问题清单。

本次追加修复没有数据库结构变更，不需要执行升级 SQL。

## 2026-06-13 任务详情 - 提取记忆结果可读化

本次更新优化工作台 AI 任务详情中 `extract_state` / “提取记忆”任务的前端预览。

### 问题原因

提取记忆任务返回的是长期状态 JSON，字段包含人物变化、关系变化、物件状态、外部压力、下一章承接要求、时间线事件等。旧前端没有专门渲染该任务类型，直接落到通用 JSON 预览，用户需要自己读字段，体验很差。

### 调整内容

- 新增“长期记忆快照”展示组件。
- 按业务字段分组展示：
  - 新增事实
  - 人物状态变化
  - 关系变化
  - 物件/资源状态
  - 伏笔更新
  - 势力变化
  - 时间线事件
  - 已回应钩子
  - 延后钩子
  - 外部压力
  - 下一章必须承接
  - 下章开场要求
  - 因果链
  - 不可替代检查
  - 章末钩子评估
  - 角色声音连续性
  - 信息揭露控制
- 顶部增加记忆条目数、人物变化数、关系变化数、承接压力数概览。
- 长文本自动换行，移动端改为单列，避免内容超出弹窗。

本次更新只改前端展示，没有数据库结构变更，不需要执行升级 SQL。

## 2026-06-12 Wizard 后端拆分 - API 层瘦身

本次更新拆分 6000 多行的 `backend/app/api/v1/wizard.py`，降低后续维护风险。

### 问题原因

旧 `wizard.py` 同时承载路由、请求模型、章节写作、弧线质量、状态抽取、上下文预算、修复保护、项目创建、审稿和任务重试等逻辑，文件超过 6000 行。继续在一个文件里改动会导致边界混乱、依赖难查、局部修改风险变高。

### 调整内容

- `backend/app/api/v1/wizard.py` 改为薄入口，只负责导出稳定的 `router`。
- 原有路由和业务编排迁移到 `backend/app/services/wizard/routes.py`。
- 请求模型拆到 `backend/app/schemas/wizard.py`。
- 写作上下文预算拆到 `backend/app/services/wizard/context_budget.py`。
- 写作控制和项目风格提示拆到 `backend/app/services/wizard/writing_controls.py`。
- 项目规划/草案格式化拆到 `backend/app/services/wizard/planning.py`。
- 章节状态、连续性载荷和状态校验拆到 `backend/app/services/wizard/state_tools.py`。
- 弧线质量、弧线章数范围、弧线桥接索引拆到 `backend/app/services/wizard/arc_tools.py`。
- 章节修复写回保护拆到 `backend/app/services/wizard/repair_guards.py`。

### 兼容性

- API 路径不变。
- 任务类型不变。
- 前端调用不需要调整。
- `app.api.v1.router` 仍然通过 `from app.api.v1.wizard import router` 引入。
- 拆分后真实导入检查确认 wizard 路由仍注册 43 个接口。

本次更新没有数据库结构变更，不需要执行升级 SQL。

### 追加更新：业务域拆分

继续将 `backend/app/services/wizard/routes.py` 从“路由 + 单体业务文件”拆成薄路由和多个业务域模块。

拆分后：

## 2026-06-12 写章节流程 - 默认快速写作与后台质检

### 问题原因

旧流程把“写章节”当成重型精修流水线处理：

- 写正文前默认调用 AI 写前诊断。
- 写正文时传入全量角色、势力和较厚项目上下文。
- 写完后立即审稿。
- 审稿低分时自动轻修，再复审。
- 写完后同步跑重状态总结，状态总结会读取全书级 story bible 和 generation context。

这会导致普通章节也产生 10 万 token 级别调用链，用户必须等待多个模型任务串行完成；更严重的是，自动修复可能把正文压缩、丢失钩子或引入新问题。

### 调整内容

- 默认写作控制切换为 `write_flow_mode=fast`。
- 默认写前检查改为规则级检查，不再每章强制调用 AI 诊断。
- 默认关闭写后同步审稿：`auto_quality_check=false`。
- 默认关闭自动轻修：`auto_light_fix=false`。
- 默认开启后台质检：`async_quality_check=true`。
- 默认开启后台状态抽取：`async_state_extract=true`。
- 写章节主任务现在只负责：
  - 读取必要上下文。
  - 生成正文和章末钩子。
  - 保存章节正文。
  - 记录后台状态抽取和审稿任务。
- 写作完成后会自动排队后台任务：
  - `extract_state`：抽取章节长期状态。
  - `audit_chapter`：刷新章节质量审稿。
- 状态抽取改为章节级上下文，不再把完整 story bible 和完整 generation context 直接交给模型。
- 写章节上下文新增预算裁剪：
  - 角色档案按本章出现、蓝图提及和主角优先排序。
  - 势力档案按本章相关性优先。
  - 卷轴大纲、状态快照、角色、势力均按预算截断。
- 精修模式仍然保留：
  - 传入 `write_flow_mode=polish`、`strict`、`quality` 或“精修”时，会启用 AI 写前诊断、同步审稿，并关闭后台异步审稿。

### 业务效果

- 普通写章不再被审稿、自动修复、复审和重状态总结串行阻塞。

## 2026-06-12 章节修复 - 防止轻修缩水和丢失钩子

本次更新修复“章节修复后 `[HOOK]` 丢失、正文从原有篇幅缩水到 2000 多字，修完还不如不修”的问题。

### 问题原因

章节写作流程会把章末 `[HOOK]` 拆到章节的 `hook` 字段里，但章节修复流程只把正文内容交给模型处理，缺少“必须保留章末钩子、不得明显压缩正文”的写回保护。模型在整章轻修时可能把场景压成摘要，导致字数缩水、钩子丢失或章节追读感被破坏。

### 调整内容

- 修复提示词新增硬规则：轻修、去 AI 味、标点修复、对白自然化等模式不得明显缩短正文，不得把场景压成梗概。

  - `quality_light_fix`、`de_ai`、`make_easy` 等轻修模式，修复后字数低于原文约 90% 会拒绝写入。

  - 模型如果返回了 `[HOOK]`，后端会自动拆出并写回章节 `hook` 字段。
  - 模型如果没有返回新钩子，会沿用原章节钩子，避免修复后钩子状态丢失。
- 评审批量修复和质量大盘章节修复都接入同一套写回保护。
- 修复输出不合格时，本次不会覆盖原文，会直接报错提示“未写入正文”。

- 弧线最后一章是否把未解压力交给下一弧线。

这两个审查只写回审查结果和修复建议，不自动改写旧正文、旧摘要或旧角色关系。

### 数据库迁移更新

新增应用内 schema migration 版本：

```text
20260609_0001 add narrative continuity columns and safe arc bridge metadata
20260609_0002 add project continuity compatibility version fields
```

新增 Alembic revision：

```text
backend/alembic/versions/20260609_0001_add_narrative_continuity_columns.py
backend/alembic/versions/20260609_0002_add_project_continuity_versions.py
```

启动时会：

1. 执行 `Base.metadata.create_all()`，保证新库能初始化。
2. 执行未应用的 schema migration。
3. 把版本写入 `schema_migrations`。

迁移策略是非破坏性的：

- 只追加字段。
- 只补结构索引。
- 不自动重写小说正文。
- 不自动重拆旧弧线。
- 不自动修改章节摘要。
- 不自动改变角色关系。
- AI 重新规划必须由用户主动触发。

### 旧小说兼容

`projects` 表新增兼容版本字段：

- `project_schema_mode`
- `arc_generation_version`
- `chapter_blueprint_version`
- `continuity_upgrade_notes`

旧项目默认保持 `legacy`。只有用户主动重新生成弧线或重新展开章节后，项目才会记录为 `continuity_v1`。

这意味着升级程序本身不会强制改写旧小说，只会让后续主动生成动作使用新的连续性规则。

### 推荐升级步骤

SQLite 本地部署：

```bash
cd backend
source .venv/bin/activate
python -m app.scripts.backup_db
pip install -r requirements.txt
python -m app.scripts.check_schema
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8001
python -m app.scripts.check_schema
```

Docker 或 PostgreSQL 部署：

1. 停止后端服务。
2. 备份数据库。
3. 拉取新代码。
4. 重新构建镜像或安装依赖。
5. 启动后端，让 migration 自动执行。
6. 使用 `python -m app.scripts.check_schema` 或数据库查询确认 `schema_migrations`。
7. 打开项目确认旧小说正文和章节仍保持原状。

## 注意事项

- 新审查接口不会自动修复问题，需要前端或调用方读取审查结果后决定是否重新生成弧线/章节。
- 旧项目不会自动升级为 `continuity_v1`，只有主动重新生成相关结构时才更新版本标记。
- 若用户已经手动改过正文或章节摘要，migration 不会覆盖这些内容。
- 后续仍建议补充 migration 单元测试、PostgreSQL 完整升级回归测试和更细的 UI 操作入口。
